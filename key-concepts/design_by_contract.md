# Design by Contract

Design by Contract (DbC) is a software correctness discipline introduced by Bertrand Meyer in the mid-1980s with the Eiffel programming language,
addressing the problem of specifying precisely - via preconditions, postconditions and invariants - what a caller must guarantee before invoking a
routine and what the routine guarantees in return, so a broken assumption is caught exactly where it occurs rather than surfacing later as an
unrelated-looking symptom.

Since `flatland 5.0.0`, `RailEnv.step()` follows such a contract: the new entry points, speed and distance of each agent are a function of its pre-step
values, its action and the conflict resolution between all agents. This page summarizes what you can rely on in each step. The steps (1)-(15) refer to
the [Runtime View RailEnv Step](key_concepts). The sections "Branch contract of the candidate methods" and "Notation" below give the branch-by-branch
contract of the implementation and its mathematical notation.

## Invariants

The following holds for every agent before and after every `step()`:

| invariant                    | description                                                                                                                                                                                           |
|------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| off map or on map            | `agent.current_entry_point` and `agent.next_entry_point` are both `None` (off map), or both set, and the next entry point is a successor of the current one (`env.rail.is_successor(current, next)`). |
| speed and distance           | `agent.speed_counter.speed` and `agent.speed_counter.distance` are `None` exactly when the agent is off map (`agent.current_entry_point is None`).                                                    |
| mutually exclusive resources | No two agents on the map hold the same resource (`env.resource_map.get_resource(current_entry_point, next_entry_point)`).                                                                             |
| done                         | An agent is done exactly when `agent.target_entry_point is not None`. It is set once, in the step the agent reaches one of its targets, and never changes afterwards.                                 |

## Preconditions

`step()` derives the following terms for each agent from its pre-step values and its action, after the malfunction counter update (1) and the new
malfunctions (2). Speed and distance are fractions of the cell length 1.

| term                 | definition                                                                                                                                                                                        |
|----------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `done`               | `agent.target_entry_point is not None`                                                                                                                                                            |
| `in_malfunction`     | `agent.malfunction_handler.in_malfunction`, i.e. the malfunction counter is greater than 0                                                                                                        |
| `off_map`            | `agent.current_entry_point is None`                                                                                                                                                               |
| `transition_invalid` | `env.rail.apply_action_independent(action, entry_point)` is `None`, where `entry_point` is the next entry point, or the initial entry point while off map. Missing actions count as `DO_NOTHING`. |
| `cell_exit`          | on map, `speed > 0` and `distance + speed >= 1`: the agent reaches the end of its cell in this step                                                                                               |
| `target_reached`     | on map, `cell_exit` and the next entry point is one of `agent.targets`                                                                                                                            |
| `ready_to_depart`    | not `done` and `agent.earliest_departure` is at most the number of this step (the first step is 1)                                                                                                |
| `map_entry`          | `off_map`, `ready_to_depart`, a moving action (`MOVE_LEFT`, `MOVE_FORWARD` or `MOVE_RIGHT`) and not `transition_invalid`                                                                          |
| `stopped`            | `speed == 0`                                                                                                                                                                                      |

## Collect phase: candidates

In the collect phase (3)-(7), each agent proposes a candidate for its entry points, speed and distance, from its own pre-step values only. Exactly one of
the following cases applies (in this order of precedence):

| case                        | condition                                | candidate entry points (current, next)              | candidate speed                      | candidate distance                                                   |
|-----------------------------|------------------------------------------|-----------------------------------------------------|--------------------------------------|----------------------------------------------------------------------|
| done                        | `done`                                   | unchanged                                           | 0                                    | `min(distance + speed, 1)` (`None` if removed)                       |
| target reached              | `target_reached`                         | (next entry point, its successor for the action)    | 0                                    | `None` if `remove_agents_at_target`, else `min(distance + speed, 1)` |
| malfunction                 | `in_malfunction`                         | unchanged                                           | 0                                    | unchanged                                                            |
| map entry                   | `map_entry`                              | (initial entry point, its successor for the action) | `min(acceleration_delta, max_speed)` | 0                                                                    |
| stay off map                | `off_map` and not `map_entry`            | (`None`, `None`)                                    | 0, set to `None` when accepted       | `None`                                                               |
| invalid action at cell exit | `cell_exit` and `transition_invalid`     | unchanged: the transition is denied                 | 0                                    | `min(distance + speed, 1)`: the agent waits at the end of the cell   |
| cell transition             | `cell_exit` and not `transition_invalid` | (next entry point, its successor for the action)    | by action, see below                 | `(distance + speed) mod 1`                                           |
| mid-cell                    | on map and not `cell_exit`               | unchanged                                           | by action, see below                 | `distance + speed`                                                   |

In the last two cases, the candidate speed depends on the action:

| action                                                        | candidate speed                              |
|---------------------------------------------------------------|----------------------------------------------|
| `MOVE_FORWARD`, or any moving action while `stopped`          | `min(speed + acceleration_delta, max_speed)` |
| `STOP_MOVING`                                                 | `max(speed + braking_delta, 0)`              |
| `DO_NOTHING`, or `MOVE_LEFT`/`MOVE_RIGHT` while not `stopped` | `speed`                                      |

The distance always advances by the pre-step speed: a speed change acts from the next step on. A `stopped` agent given a moving action gets its speed in
this step and moves from the next step on. Since `cell_exit` requires `speed > 0`, a `stopped` agent at the end of its cell never falls into "invalid action
at cell exit": it is promoted optimistically, and the crossing is only tried, and possibly denied, in the next step.

## Distribute phase: candidates accepted or discarded

The resource check (10) resolves the conflicts between all candidates. In the distribute phase (11)-(13), each agent's candidate is then accepted or
discarded:

| case              | condition                                                                          | entry points               | speed              | distance                   |
|-------------------|------------------------------------------------------------------------------------|----------------------------|--------------------|----------------------------|
| accepted, on map  | granted, and the candidate is on map and not a target that the agent is removed at | candidate                  | candidate          | candidate                  |
| accepted, off map | granted, and the candidate is off map, or a target with `remove_agents_at_target`  | (`None`, `None`)           | `None`             | `None`                     |
| denied crossing   | not granted, on map                                                                | unchanged                  | 0                  | `min(distance + speed, 1)` |
| denied map entry  | not granted, off map                                                               | unchanged (`None`, `None`) | unchanged (`None`) | unchanged (`None`)         |

An agent that stays within its cell is always granted. A denied agent waits at the end of its cell with speed 0 and has to accelerate again.
Once accepted, `handle_done_state` (14) sets `agent.target_entry_point` if the agent has reached a target, and removes the agent from the map if
`remove_agents_at_target` is set.

## Branch contract of the candidate methods

Branch-by-branch comparison of `AbstractRailEnv._candidate_entry_points()`, `_candidate_speed()` and
`_candidate_distance()` (`flatland/envs/rail_env.py`). All three are pure, pre-step-only derivations of this
step's optimistic candidate entry points/speed/distance, called from the collect phase and cross-checked by the
post-step postcondition checks. `_candidate_entry_points` is the *producer*: it derives `off_map`/`cell_exit`/
`target_reached`/`map_entry` from scratch and returns the resolved `candidate_entry_point`. `_candidate_speed`/
`_candidate_distance` are *consumers*: they take that resolved `candidate_entry_point` as an input parameter
rather than re-deriving it. That asymmetry is why some terms/branches can be made textually identical across all
three, and others structurally can't - noted case by case below.

Every branch condition is written to be self-contained (order-independent), and for every case shared between
`_candidate_speed`/`_candidate_distance`, textually identical. `_candidate_entry_points`' shared branches
(Done/Malfunction/Map entry/Stay off map/Invalid action at cell exit) use the same exclusion structure and
branch order as the other two; its own Target reached/Map entry/On-map cell transition necessarily keep their
own richer, from-scratch derivations.

`Stopped`/`Acceleration or start moving`/`Braking` are not a clean fusion between speed and distance: distance
partitions this region by physical state (`stopped` or not), speed partitions the same region by the
action given that step. Neither is a subset of the other - the two methods reach the same practical outcomes
via different, non-corresponding branches there. `_candidate_entry_points` doesn't partition this region at
all - it only cares whether a genuine crossing is happening (`cell_exit` + a valid action), which is
orthogonal to both speed's and distance's split.

Since `cell_exit` requires `speed > 0` (see Table 2a), `invalid_action_at_cell_exit` can never be true
while `stopped` - a `STOPPED` agent given a moving action always falls through **Invalid action at cell exit**
into **Acceleration or start moving**, regardless of whether that action is itself structurally valid (e.g. a
non-L/R action at a symmetric switch). This is intentional: it is what lets a `STOPPED` agent banked at a
switch boundary optimistically resume `MOVING` on any moving-action retry, exactly like an ordinary
resource-check-blocked agent already does elsewhere - the *next* step then genuinely re-attempts the crossing
(now with `speed > 0`), and is denied and re-charged again if the action is still invalid. The penalty is
per genuine entering attempt, not per retry (see `BaseDefaultRewards.step_reward` in `rewards.py`).

### Branch order (as they appear in code)

The branch labels below are the code comments immediately above each `if` in
`flatland/envs/rail_env.py`, in on-disk order - a quick index into Table 1's rows as they're actually
laid out method by method. Per the note at the top of each method's own branch section, this order is
cosmetic (every branch condition is self-contained and pairwise disjoint - see the branches themselves
for the exclusion reasoning), not load-bearing.

```
_candidate_entry_points          _candidate_speed                  _candidate_distance
------------------------         ------------------------          ------------------------
done                             done                              done
off_map_no_departure             stay off map                      stay off map
keep moving mid-cell             keep moving mid-cell              keep moving mid-cell
on-map cell transition           acceleration or start moving      stopped
malfunction                      braking                           malfunction
map entry                        malfunction                       map entry
target reached                   map entry                         target reached
invalid action at cell exit      target reached                    invalid action at cell exit
                                 invalid action at cell exit
```

Reordered by empirical branch frequency ([`5a19eaf9`](https://github.com/flatland-association/flatland-rl/commit/5a19eaf9)): `off_map_no_departure`/`stay off map` is the
single largest branch across every profiled scenario (42-87% of calls), so it's checked right after
`done` rather than last among the off-map-only branches - purely a performance reordering, not a
semantic one (see the note above: every condition is self-contained, so this order is cosmetic).

Each method's final branch (`invalid action at cell exit`) is an explicit `if`, not an implicit `else`,
followed by a `raise ValueError(...)` that is unreachable by construction (the branches are exhaustive as
well as disjoint).

```
stay_off_map (candidate_entry_point is None)
⟺ off_map ∧ (
done                                              -- Done
∨ (¬done ∧ in_malfunction)                        -- Malfunction (MALFUNCTION_OFF_MAP)
∨ (¬done ∧ ¬in_malfunction ∧ off_map_no_departure) -- off_map_no_departure
)
```

`required_action_invalid_or_not_required_or_no_movement` breaks down into three disjoint cases - why an
off-map agent doesn't depart this step:

- **not yet ready to depart** (`¬ready_to_depart`) - state not yet `READY_TO_DEPART`, an action isn't
  required yet.
- **ready to depart but no moving action given** (`ready_to_depart ∧ ¬movement_action_given`) - e.g.
  `DO_NOTHING`, an action was required but a departure wasn't attempted.
- **a moving action given that doesn't resolve to a valid transition on the rail**
  (`ready_to_depart ∧ movement_action_given ∧ transition_invalid`) - an action was required,
  attempted, and invalid.

### Table 3 — distribute phase: candidate accepted or discarded

Tables 1, 2a and 2b are the *collect* phase: purely optimistic, pre-step-only derivations, computed for every agent before
any conflict is resolved. `RailEnv.step()`'s distribute phase then resolves conflicts via `MotionCheck`
(`resource_check = self.resource_check.check_resource(i_agent)`) and, per agent, either commits the already-computed
`candidate_entry_point`/`candidate_next_entry_point`/`candidate_speed`/`candidate_distance` as-is or falls back to a
discarded-candidate formula - this is `step()`'s (12) POSITION UPDATE and (13) SPEED_COUNTER UPDATE blocks.
`agent.old_entry_point` is this step's stable pre-step snapshot (captured before (12) touches anything) of
`current_entry_point`, i.e. `off_map` (Table 2a) - (13)'s own discarded-candidate branch reads it to tell
"was this agent on or off map going into this step" apart: `pass` (a true no-op, not just an unchanged-value
assignment) is only correct off map because the `speed_counter` invariant already holds `(None, None)` there, with
nothing to reset.

| Case                          | Condition                                                                                                                          | Speed (`speed_counter.speed`)                                                           | Distance (`speed_counter.distance`)                                                                                                                                                                | Entry points (`current_entry_point`, `next_entry_point`)                                                                                                                                                                          |
|-------------------------------|------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

**Accepted, ends up off map** merges two underlying branches (target reached and removed vs. stayed off map) that
have distinct conditions but always resolve to the identical `(None, None, (None, None))` triple: `_candidate_speed`
never returns `None` itself - it returns `0` for both underlying branches (Table 1) - so (13) forces `None` in
both, overriding the already-computed `agent_transition_data.candidate_speed`, to match the invariant that a
removed/off-map agent's speed must be `None`. Distance needs no such forcing, since `_candidate_distance` already
returns `None` for both directly (Table 1).

#### `SpeedCounter.is_cell_entry` — derived after Table 3 resolves speed/distance

`SpeedCounter.set(speed, distance)` (`step_utils/speed_counter.py`) is what (13) actually calls to commit each
row of Table 3 above - it doesn't just store the two values, it also derives `is_cell_entry`, a boolean tracked
alongside them: `True` exactly when the agent just bootstrapped onto the map (pre-step `distance is None`, new
`distance is not None`), or the pre-step `distance`/`speed` pair implies a crossing was attempted
(`pre_distance + pre_speed >= SEGMENT_LENGTH`) *and* the post-step `distance` lands inside the fresh cell rather
than banked at the exit (`distance < SEGMENT_LENGTH`). Both conjuncts are needed: at `speed == SEGMENT_LENGTH`
(e.g. `max_speed=1`), `distance_after_crossing`'s modulo wraps exactly back to the pre-step value (`0 -> 0`), so a
plain `distance < pre_distance` (or even `<=`) comparison misclassifies it - the latter also misfires on a
stopped/banked agent whose distance is unchanged for an unrelated reason (denied at the boundary, or genuinely at
rest).

This is a distinct term from `cell_exit`/`is_cell_exit()` (Table 2a) despite the similar name: `cell_exit` is a
collect-phase precondition computed from the *pre-step* speed/distance, feeding `_candidate_entry_points`; `is_cell_entry`
is derived *after* Table 3 has already resolved this step's accepted-or-discarded speed/distance, from both the
pre- and post-step values together. `action_required` (`rail_env.py`) takes a parameter literally named
`is_cell_entry` that in fact always receives `is_cell_exit()`'s value, not `SpeedCounter.is_cell_entry` - see its
own docstring for that pre-existing naming mismatch. `SpeedCounter.is_cell_entry` itself isn't consulted by any
production control flow at the time of writing - only asserted on directly by `tests/test_speed_counter.py`.

### Collect phase

`AbstractRailEnv.collect()` computes the candidates in `_candidate_entry_points()`, `_candidate_speed()` and `_candidate_distance()` (steps (3)-(7)).
The cases are tried from top to bottom, with $\tau = \tau(p', \action_i^t)$ on map and $\tau = \tau(p_{i,1,1}, \action_i^t)$ off map:

$$
\tilde c_i^{t+1} =
\begin{cases}
c_i^t & i \in dones^t \quad \text{(done)} \\
(p', \tau) & \mathit{cellExit}_i^t \wedge p' \in targets_i \quad \text{(target reached)} \\
c_i^t & m_i^t \neq \bot \quad \text{(malfunction)} \\
(p_{i,1,1}, \tau) & c_i^t = \bot \wedge e_{i,1,1} \leq t+1 \wedge \action_i^t \in \{\text{L},\text{F},\text{R}\} \wedge \tau \neq \bot \quad \text{(map entry)} \\
\bot & c_i^t = \bot \quad \text{(stay off map)} \\
c_i^t & \mathit{cellExit}_i^t \wedge \tau = \bot \quad \text{(invalid action at cell exit)} \\
(p', \tau) & \mathit{cellExit}_i^t \quad \text{(cell transition)} \\
c_i^t & \text{otherwise (mid-cell)}
\end{cases}
$$

$$
\tilde s_i^{t+1} =
\begin{cases}
0 & \text{done, target reached, malfunction, stay off map or invalid action at cell exit} \\
\min\{\Delta{}v_a, v_{\text{max},i}\} & \text{map entry} \\
\min\{s_i^t + \Delta{}v_a, v_{\text{max},i}\} & \action_i^t = \text{F} \vee (s_i^t = 0 \wedge \action_i^t \in \{\text{L},\text{F},\text{R}\}) \\
\max\{s_i^t + \Delta{}v_b, 0\} & \action_i^t = \text{S} \\
s_i^t & \text{otherwise}
\end{cases}
$$

$$
\tilde d_i^{t+1} =
\begin{cases}
\min\{d_i^t + s_i^t, \lVert c_i^t \rVert\} & \text{done, invalid action at cell exit, or target reached} \wedge \neg\mathit{removeAtTarget} \\
\bot & \text{target reached} \wedge \mathit{removeAtTarget} \text{, or stay off map} \\
d_i^t & \text{malfunction, or } s_i^t = 0 \\
0 & \text{map entry} \\
(d_i^t + s_i^t) \bmod \lVert c_i^t \rVert & \text{otherwise (cell transition or mid-cell)}
\end{cases}
$$

### Distribute phase

`AbstractRailEnv.distribute()` accepts or discards the candidates (steps (11)-(13)), where $\mu_i := \mu(\tilde c_i^{t+1}, \action_i^t) = \top$ means the
candidate is granted by the resource check (10), $\tilde p$ is the candidate current entry point, and
$R_i := \mathit{removeAtTarget} \wedge (i \in dones^t \vee \tilde p \in targets_i)$ means the agent is removed at its target:

$$
c_i^{t+1} =
\begin{cases}
\tilde c_i^{t+1} & \mu_i \wedge \neg R_i \\
\bot & \mu_i \wedge R_i \\
c_i^t & \neg \mu_i
\end{cases}
$$

$$
s_i^{t+1} =
\begin{cases}
\tilde s_i^{t+1} & \mu_i \wedge \neg R_i \wedge \tilde c_i^{t+1} \neq \bot \\
\bot & \mu_i \wedge (R_i \vee \tilde c_i^{t+1} = \bot) \\
0 & \neg \mu_i \wedge c_i^t \neq \bot \\
\bot & \neg \mu_i \wedge c_i^t = \bot
\end{cases}
$$

$$
d_i^{t+1} =
\begin{cases}
\tilde d_i^{t+1} & \mu_i \\
\min\{d_i^t + s_i^t, \lVert c_i^t \rVert\} & \neg \mu_i
\end{cases}
$$

with $\min\{\bot + \bot, \lVert c_i^t \rVert\} = \bot$ off map. `handle_done_state()` (14) sets $\theta_i^{t+1}$ to the new current entry point when it is
one of $targets_i$, and $\theta_i^{t+1} = \theta_i^t$ otherwise, so that $i \in dones^{t+1} \iff \theta_i^{t+1} \neq \bot$; with $\mathit{removeAtTarget}$, it
then removes the agent ($c_i^{t+1} = \bot$ above). The malfunction counter is decremented at the start of the next step (1),
$m_i^{t+1} = \bot$ if $m_i^t = \bot$ or $m_i^t = 1$, else $m_i^t - 1$, before the effects generator may start a new malfunction (2).

## Checking the contract at runtime

`RailEnv(check_step_pre_post_conditions=True)`, the default, lets `step()` check its contract in every step (`GraphRailEnv` runs the same checks, on by
default):

| when                         | what is checked                                                                                                                                                                                    |
|------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| at the start of `step()`     | the invariants above, for the state left behind by the previous step                                                                                                                               |
| in the collect phase         | each candidate is off map or on map: both entry points `None`, or the next one a successor of the current one                                                                                      |
| at the end of `step()`       | the invariants again, and the postconditions: the new entry points, speed and distance of each agent are the ones the tables above give for its pre-step values, its action and the resource check |
| `RailEnvStateMachineWrapper` | in addition, after the state machine update: `agent.state` equals `agent.derived_state(...)`, and, unless done, the agent is in a malfunction state exactly when it is in malfunction              |

A violation raises an `AssertionError`. This catches a broken state early, e.g. when a custom effects generator or another hook modifies the agents
between steps. The checks are plain `assert` statements, so they are also skipped when Python runs with `-O`.

The checks recompute the candidates of all agents, which makes `step()` slower. For training and other performance-sensitive runs, turn them off, either in
the constructor or on an existing env, e.g. one created by `env_generator()`, loaded with `RailEnvPersister.load_new()` or a `GraphRailEnv`, which do not
take the flag:

```python
env = RailEnv(..., check_step_pre_post_conditions=False)
# or
env.check_step_pre_post_conditions = False
```

Turning the checks off does not change the simulation: the same actions lead to the same entry points, speeds and distances.
